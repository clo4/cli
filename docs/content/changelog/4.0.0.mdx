This release adds `loadSpec`, which builds a subcommand only when a command line enters it. It also fixes shell completion of values that contain spaces, colons, quotes or shell syntax. The major version is for the spec checks that `@clo4/cli/testing` no longer exports. If you don't call those checks yourself, upgrading needs no code changes.

## Breaking changes

- `@clo4/cli/testing` exports only `test`, `testSpec` and the types of their options. The 17 `assert*` functions are gone, including `assertPlusMinusOptionsTakeOneArg` and `assertRequiresSeparatorTakesOneArg`, which 3.0 deprecated. Replace a call to one of them with `testSpec(spec)`, which runs every check. With `namingStyle: "function"`, each test step still shows the name of its check, such as `assertNamesReadBack`.

## Added

- A subcommand can have a `loadSpec` function, which returns the rest of that command's spec. The parser, help and completion call it the first time they enter the command, and never again. `demo remote add`, `demo help remote` and pressing Tab after `demo remote` all load `remote` and none of the other commands.

  ```ts
  subcommands: [
    {
      name: "remote",
      description: "Manage remotes.",
      loadSpec: () => import("./remote.ts").then((module) => module.default),
    },
  ],
  ```

- The subcommand keeps its `name`, `description`, `hidden` and `isPersistent`, because its parent's help and completion show it before it loads. `loadSpec` returns everything else, such as `args`, `options`, `subcommands` and `action`. The new `CommandBody` type describes that object.
- `loadSpec` can return the object directly, or a promise of it from `import()`. `run` waits only when a command on the command line returns a promise.
- `testSpec` calls every `loadSpec` before it checks the spec.

Above about 50 commands, `loadSpec` makes a CLI start faster. These times are for running one command of a CLI bundled into one file, whose commands each take 6 options, on an Apple M3 Pro. A file per group means each group's `import()` is a separate chunk. The times leave out Node's startup and the time it spends setting up stdout.

| Commands | No `loadSpec` | Body from the same file | Body from a file per group |
| -------- | ------------- | ----------------------- | -------------------------- |
| 10       | 1.5 ms        | 1.6 ms                  | 1.8 ms                     |
| 50       | 1.9 ms        | 1.9 ms                  | 1.9 ms                     |
| 100      | 2.3 ms        | 2.1 ms                  | 1.9 ms                     |
| 1,000    | 12.6 ms       | 7.5 ms                  | 2.1 ms                     |

## Fixed

- `helpCommand` reads the command names it's given the same way the parser reads a command line. `demo help leaf status` shows help for `status` when `leaf` inherits `status` as a persistent subcommand. A name that doesn't match prints the same error and suggestion as running the command.
- Completion after `demo help leaf` offers the persistent subcommands that `leaf` inherits.

## Completion improvements

The CLI now formats completion candidates for each shell, and each completion script passes `--shell` to say which. Scripts generated by 3.x keep working with a 4.0 CLI. Users of your CLI get these fixes once they save the script again, such as with `demo completion bash > ~/.demo-completion.bash`.

- Bash no longer runs expansions, such as `$(...)`, that a candidate contains. The old script passed candidates through `compgen -W`, which expanded them. The CLI now escapes spaces and shell syntax in each value Bash inserts.
- Zsh completes a value that contains a colon. The old script split the value at the colon and showed the rest as its description.
- Zsh completes a word you started inside quotes.
- PowerShell quotes values that contain curly single quotes, which PowerShell also reads as quotes.
- Completion leaves out values that contain a tab or line break, because a shell reads each candidate as one line. Tabs and line breaks in descriptions become spaces.
