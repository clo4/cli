Version 7 introduces a minimal parser combinator API for text transformations. Combining parsers gives you a parser. Transforming its output with `.map` gives you a parser too.

The result fits the existing `parse` field. It also retains the structure of its input, which help, errors and completion can all use.

Consider `--timeout 30s`. Your action wants milliseconds. Help needs to explain the unit suffixes, and completion needs to know what can follow `30`. Those are three uses of the same format, so they can all come from one definition.

## Parsing a duration

A parser reads text and returns a value. A parser combinator is a function that builds a parser from smaller ones. For a duration, those pieces are a number and a unit:

```ts
import { choice, seq, uint } from "@clo4/cli";

const duration = seq(uint, choice("ms", "s", "m", "h"));
```

`uint` reads a whole number without a sign. `choice` reads one of the unit strings. `seq` runs them in sequence and returns their results as a tuple. For `30s`, that is `[30, "s"]`, with the inferred type `[number, "ms" | "s" | "m" | "h"]`.

Use `.map` to turn that result into milliseconds:

```ts
const millisecondsPerUnit = { ms: 1, s: 1_000, m: 60_000, h: 3_600_000 };
const milliseconds = duration.map(([amount, unit]) => amount * millisecondsPerUnit[unit]);
```

Now `30s` gives `30000`, and `2m` gives `120000`. The result of `.map` is another parser, with `number` as its output type. It can be part of another parser just as `uint` was part of `duration`.

The same operations can produce objects and arrays:

```ts
import { sepBy } from "@clo4/cli";

const size = seq(uint.as("width"), "x", uint.as("height")).asObject();
// "1920x1080" → { width: 1920, height: 1080 }

const scopes = sepBy(choice("read", "write", "admin"), ",");
// "read,write" → ["read", "write"]
```

Strings in `seq`, such as `"x"`, match literal text and stay out of the result. `.as` labels a parser, and `.asObject()` returns each labelled value of a `seq` under its label, with the inferred type `{ width: number; height: number }`. Help shows the same labels, as `<width>x<height>`. `sepBy` builds a list parser from an existing parser and a separator. There are also functions for optional parts, repetition and text between separators.

## Help and completion use the parser

Put `milliseconds` in an argument's `parse` field:

```ts
{
  name: "--timeout",
  description: "Time to wait for a response",
  args: {
    name: "duration",
    default: "30s",
    parse: milliseconds,
  },
}
```

With this option in a spec, `--timeout 2m` gives the action `120000`. TypeScript infers `number` for `options.get("--timeout")`. The default goes through the same parser, so omitting the option gives `30000`.

The transformation changes what the action receives while preserving how the input is read. Help follows the parser's parts, so it still shows the number and unit suffixes:

```console
  --timeout <duration>  Time to wait for a response (<int>(ms|s|m|h), default: 30s)
```

If the user enters `30x`, the error identifies the part that did not match:

```console
Error: Invalid value "30x" for --timeout: expected ms | s | m | h after "30"
```

With shell completion installed, Tab after `--timeout 30` offers `30ms`, `30s`, `30m` and `30h`. Completion reads as far as it can into the value, then uses the strings expected at that position. For the `scopes` parser above, `read,w` completes to `read,write`.

`choice` already knows which units it accepts, and `seq` already knows where they belong. Help uses those parts as a pattern. Errors and completion use what the parser expects at the position it reaches. `.map` wraps that structure, so each system can still use it after the result becomes a number.

An argument still has one `parse` field, and the action still receives its result. The structure from composition feeds the existing help and completion systems. Adding a unit to `choice` updates the accepted syntax, help, errors and completion together.

## Built for a CLI's first run

A CLI often starts, constructs its spec, parses a few values and exits. Shell completion starts it again on Tab. Parser construction and the first parse are part of the normal workload, so the implementation needs to keep those costs small.

The combinators construct small objects that hold their parts. Parsing uses shared functions for each kind of part and walks the input by position. `uint` accumulates ordinary integers digit by digit. Help patterns and error messages are formatted on the paths that need them, and commands without argument parsers skip the value conversion path.

I measured matching minified builds of 6.1.2 and v7 on an Apple M3 Pro with Node 26.3.0:

| Work                                                    | Median  |
| ------------------------------------------------------- | ------- |
| Import 6.1.2                                            | 0.90 ms |
| Import v7                                               | 1.01 ms |
| Construct the duration parser and its command spec      | 0.02 ms |
| Run that command for the first time, after construction | 0.54 ms |

Each row has 200 samples. Every sample runs in a fresh Node process, with Node's compile cache disabled. The last two rows use the duration-to-milliseconds parser above in a command with one `--timeout` option and an action that reads its value. Times exclude Node's own startup and output.

The minified library grows from 39.0 kB to 46.2 kB. Importing it costs about 0.11 ms more in this measurement, including for a CLI that does not use the new parsers.

The [parser guide](https://clo4.net/cli/next/parsers) walks through a complete command and the rest of the API. Schemas from Zod, ArkType and Valibot still work in `parse` as they did in 6.1.

## Upgrading from 6.1

`choice` now takes separate arguments so it can accept parsers as well as strings. Update calls that pass an array:

```ts
CLI.choice(["debug", "release"]); // 6.1
CLI.choice("debug", "release"); // 7.0

CLI.choice(...regions); // Spread an existing array.
```

`number()` now requires a digit after a decimal point. It rejects `3.`, but still accepts `.5` and `3.0`. This lets `seq(number(), "..", number())` read a range such as `1..5`.

If your tests compare help, errors or completion output, these changes can also affect them:

- Integer constraints in help use `int` instead of `integer`.
- An integer outside JavaScript's safe range reports the limit, such as `too large, the limit is 9007199254740991`, instead of `expected an integer`.
- Completion for `choice` only offers values that start with the text already typed.
- Messages from `assertDefaultsPassTheirParse` and `assertRangesAreNotEmpty` use `parser` instead of `parse`.
