Introducing v6.1.0, bringing basic support for custom argument value parsers.

Actions previously received all values as strings. Take `--port`: this clearly needs a number, and clearly within a defined range. Previously, you'd have to convert it in the action, validate the range yourself, and handle the error yourself too. Now, you can give arguments a `parse` property, taking a "standard schema" and returning its parsed output as the argument value.

This library includes two parsers, purpose built for the most common command-line parsing tasks, but you can use anything that implements the standard schema interface (e.g. Zod, Valibot, ArkType).

```ts
import * as CLI from "@clo4/cli";

const spec = CLI.spec({
  name: "serve",
  args: { name: "root", description: "Folder to serve" },
  options: [
    CLI.help,
    {
      name: "--port",
      description: "Listen on this port",
      args: {
        name: "port",
        default: "8080",
        parse: CLI.number({ min: 1, max: 65535, int: true }),
      },
    },
    {
      name: "--mode",
      description: "Build mode",
      isRequired: true,
      args: {
        name: "mode",
        parse: CLI.choice(["debug", "release"]),
      },
    },
  ],
  action({ args: [root], options }) {
    options.get("--port"); // number
    options.get("--mode"); // "debug" | "release"
  },
});

CLI.run(spec);
```

`CLI.number` and `CLI.choice` are built in. The default `"8080"` goes through `parse` like a value the user typed, so your action gets the number `8080`.

## All errors are now shown at once

Any errors accumulated from running parsers or from the command-line parser itself are now presented simultaneously. Previously, the library would stop at the first error as a performance optimisation, but this results in a worse user experience because you needed to make N+1 attempts to run a command, where N is the number of errors you made. Now it's constant, 2: make a mistake, fix your errors, and you're on your way.

```console
$ serve --port 70000 --mode fast
Error: Expected 1 argument
Error: Invalid value "70000" for --port: expected an integer from 1 to 65535
Error: Invalid value "fast" for --mode: expected debug | release

Usage:
  serve --mode <mode> [flags] <root>

Arguments:
  root  Folder to serve

Flags:
  -h, --help     Print a help message
  --port <port>  Listen on this port (integer from 1 to 65535, default: 8080)
  --mode <mode>  Build mode (debug | release)
```

Note: if an unknown option is provided, it will be the only error reported, because the parser can't tell what the words after it mean. The worst case would be executing an action when the user was intending to tweak some aspect of its execution.

## Using Zod, ArkType and Valibot

`parse` takes any [Standard Schema](https://standardschema.dev), the shared interface that Zod, ArkType, Valibot and other validation libraries implement. If you already validate config or API input with one of them, your command line can use the same schemas:

```ts
import { type } from "arktype";
import { z } from "zod";
import * as CLI from "@clo4/cli";

const spec = CLI.spec({
  name: "deploy",
  options: [
    CLI.help,
    {
      name: "--region",
      description: "Region to deploy to",
      args: { name: "region", parse: z.enum(["us-east", "eu-west", "ap-south"]) },
    },
    {
      name: "--replicas",
      description: "Number of replicas",
      args: { name: "count", default: "2", parse: z.coerce.number().int().min(1).max(10) },
    },
    {
      name: "--env",
      description: "Environment",
      args: { name: "env", parse: type("'production' | 'staging'") },
    },
  ],
  subcommands: [CLI.completion],
  action({ options }) {
    options.get("--region"); // "us-east" | "eu-west" | "ap-south" | undefined
    options.get("--replicas"); // number
    options.get("--env"); // "production" | "staging" | undefined
  },
});

CLI.run(spec);
```

Async schemas work too, and will be executed concurrently. A rejected value shows the schema's error message:

```console
$ deploy --replicas 40
Error: Invalid value "40" for --replicas: Too big: expected number to be <=10
```

Help and completion read a schema's choices and number range from the JSON Schema it returns from `~standard.jsonSchema`, the same way they read `CLI.number` and `CLI.choice`. Zod and ArkType schemas have it with no setup, so you don't need to list their values in the option's description. The tests cover Zod 4.6 and ArkType 2.2:

```console
$ deploy --help
Usage:
  deploy [flags]

Commands:
  completion  Print a shell completion script

Flags:
  --region <region>   Region to deploy to (us-east | eu-west | ap-south)
  --replicas <count>  Number of replicas (integer from 1 to 10, default: 2)
  --env <env>         Environment (production | staging)

Global flags:
  -h, --help          Print a help message
```

Pressing Tab after `--region` offers `us-east`, `eu-west` and `ap-south`, and after `--env` it offers `production` and `staging`.

Valibot schemas have no `~standard.jsonSchema`, so they parse values and add nothing to help or completion. For a Valibot schema, list the values in the option's description and give the argument a `suggestions` array.

## Why not plain functions?

I've thought long and hard about this. Ultimately, I decided against supporting plain functions for parsers because using libraries that implement standard schema push you into a pit of success, and conversely, plain functions make it too easy to make a crappy user experience. Essentially, standard schema makes the default UX _too good_ to justify the comparatively normal UX of a plain function.

If you _desperately_ want to use a plain function, ask your LLM of choice to generate you a function that takes a function and returns a schema from it. But if I were you, I would seriously consider if that's actually the right thing to do.

## Upgrading

There are no changes to the library that will impact specs written on version 6.0.0.

The minified bundle grew from 33.5 kB to 39.2 kB, and importing it takes 0.09 ms longer, even in a CLI that doesn't use `parse`. The [release notes](https://github.com/clo4/cli/releases/tag/v6.1.0) have the benchmark details, the new spec checks and the full list of changes.
