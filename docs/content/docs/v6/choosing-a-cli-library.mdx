title: Choosing a CLI library
description: Compare the responsibilities of the library and your application.

`@clo4/cli` handles command-line syntax, inferred action types, help and shell completion. Actions handle value conversion, application setup and the work of each command.

This division keeps application code in ordinary functions. It also means that features such as validation and lifecycle hooks are responsibilities you keep in your code.

## Value conversion and validation

An action receives strings. To accept a number, parse it. To restrict a value to a set, test it:

```ts
import * as CLI from "@clo4/cli";

const spec = CLI.spec({
  name: "deploy",
  options: [
    {
      name: "--mode",
      description: "Build mode: debug or release.",
      args: { name: "mode", default: "debug", suggestions: ["debug", "release"] },
    },
  ],
  action({ options }) {
    const mode = options.get("--mode");
    if (mode !== "debug" && mode !== "release") {
      throw new Error("--mode must be debug or release");
    }
    // mode is now "debug" | "release".
    console.log(mode);
  },
});

CLI.run(spec);
```

The description tells users which values are valid. Suggestions offer those values during completion. The action enforces the restriction. Neither help nor completion inspects the action's code.

Yargs provides `coerce` and `choices`. citty provides enum arguments. Commander supports custom option processing. If you want conversion and validation in the command definition, those APIs offer a different approach.

## Setup and cleanup

Call setup code from an action. Use `try` and `finally` for resources that need cleanup. Shared setup can be a function called by several actions.

Commander provides lifecycle hooks such as `preAction`. citty provides `setup`, `cleanup` and plugins for shared hooks. `@clo4/cli` has no lifecycle hooks or built-in plugin system.

oclif also provides a project generator, packaging tools and user-installable plugins. A CLI that needs those facilities must provide them itself with `@clo4/cli`, or choose a framework that includes them.

## Completion

`@clo4/cli` generates completion for Bash, Zsh, Fish, PowerShell and Nushell. A custom generator belongs to the argument it completes. The library selects the argument, calls its generator and formats the results for the shell.

Commander and citty have no built-in shell completion. oclif provides completion through a separate plugin. Yargs uses a custom completion function for the CLI rather than a generator attached to each argument.

[Generate completion suggestions](./completion-generators.mdx) shows a custom generator. [Install shell completion](./install-completion.mdx) covers shell setup.

## Type inference

`CLI.spec` infers action inputs from plain command objects. Types include positional argument counts, defaults and persistent options inherited by inline commands. A separately defined `CLI.command` infers its own options but cannot infer options from a parent outside its definition.

Commander offers inference through `@commander-js/extra-typings`. Yargs 18 does not ship types, and the `@types/yargs` package targets Yargs 17. The comparisons here refer to the versions used in this repository: Commander 15.1, citty 0.2.2, Yargs 18.2 and `@oclif/core` 5.1.

`@clo4/cli` is ESM-only. Its inference requires TypeScript 6.0 or later.

## Startup

Short commands and shell completion spend a larger fraction of their time starting up. Every completion request starts a new CLI process.

In the repository's benchmarks, citty takes 1.6–1.8 times as long as `@clo4/cli` for the measured work. Commander takes 3.4–4.4 times, oclif 16.0–16.2 times and Yargs 18.0–20.7 times. [Performance](./performance.mdx) describes the workload and exclusions.

For larger CLIs, `loadSpec` defers command construction or imports until a run needs them. This also keeps root help and completion from loading every command.

## Spec format

The field names come from Fig's autocomplete spec format. The [withfig/autocomplete](https://github.com/withfig/autocomplete) repository contains examples of that format for hundreds of tools.

`@clo4/cli` continues [clo4/fig-cli](https://github.com/clo4/fig-cli), started in April 2022. Its supported fields are listed in the [API reference](./reference/index.mdx).
