## Loading commands on demand

A spec is built in full every time the CLI starts, even though one run uses one command. Give a subcommand a `loadSpec` function that returns the whole command, and the command is built only when a command line enters it:

```ts
subcommands: [
  {
    name: "remote",
    description: "Manage remotes.",
    loadSpec: () => import("./remote.ts").then((module) => module.default),
  },
],
```

```ts
// remote.ts
import * as CLI from "@clo4/cli";

export default CLI.command({
  name: "remote",
  requiresSubcommand: true,
  subcommands: [
    { name: "add", description: "Add a remote.", args: { name: "url" }, action: addRemote },
    { name: "list", description: "List remotes.", action: listRemotes },
  ],
});
```

The command with the `loadSpec` sets only its `name`, `description`, `hidden` and `isPersistent`, because its parent's help and completion show it before it loads. Everything else goes in the loaded command: `args`, `options`, `subcommands`, `action`, `requiresSubcommand` and `parserDirectives`. A subcommand of a loaded command can have a `loadSpec` of its own.

The loaded command is an ordinary command, so it has the same `name`. It can leave out `description`, `hidden` and `isPersistent`. If it sets one, the command with the `loadSpec` has to set it to the same value, and `testSpec` fails when the two differ. `testSpec` also fails when a command sets anything else beside its `loadSpec`.

`loadSpec` runs when the parser, help or completion enters the command, once for each command line. `demo remote add`, `demo remote --help`, `demo help remote` and pressing Tab after `demo remote` all load `remote` and nothing else. `demo --help` loads nothing.

Loading never changes your spec. The parser carries on with a copy of the loaded command, with the `name`, `description`, `hidden` and `isPersistent` of the command that has the `loadSpec` on top, and that copy is the command on an action's `path`.

`loadSpec` can also return the command directly, which keeps it in the same file and the parser synchronous:

```ts
loadSpec: () => CLI.command({ name: "remote", requiresSubcommand: true, subcommands: [/* ... */] }),
```

Write the `import()` in your own file with a literal path, as above, so a bundler can find the file and emit it as a separate chunk.

Call `CLI.run` without `await`, as every example here does. A command's file can't import the library from an entry that is waiting on a top-level `await`, so a bundler moves the library into a file of its own, and every run loads one more file.

An action that calls `help({ path })` for another command loads the commands on that path too. `help` returns a string, so it can't wait for a `loadSpec` that returns a promise, and throws an error with the command's name in its message. The commands on the action's own `path` are loaded already.

`testSpec` loads every command and checks the loaded CLI, whatever else has used the spec before.

### When loading on demand is faster

Loading from another file costs about 0.3 ms, the time Node takes to read one more file. It's faster than building the whole spec from about 50 commands up, which is also about when a spec gets easier to maintain as a file per command group. Returning the command from the same file is faster from about 25 commands, and costs 0.03 ms below that.

These times are for running one command of a bundled CLI whose commands each take 6 options, on an Apple M3 Pro. They leave out Node's own startup and the time it spends setting up stdout.

| Commands | No `loadSpec` | Command from the same file | Command from a file per group |
| -------- | ------------- | -------------------------- | ----------------------------- |
| 10       | 1.6 ms        | 1.7 ms                     | 1.9 ms                        |
| 50       | 1.9 ms        | 1.9 ms                     | 2.0 ms                        |
| 100      | 2.4 ms        | 2.2 ms                     | 2.0 ms                        |
| 1,000    | 12.9 ms       | 7.8 ms                     | 2.3 ms                        |

The benchmark compares large CLIs in two forms, one file and a file per group. Each form has a table for each kind of work: running a command, root help, a group's help, and an unknown command. Each library is written the way its own docs show for that form, and a hand-written `parseArgs` CLI shows the least a CLI can do. In one file, @clo4/cli returns each group from `loadSpec`. The benchmark also records @clo4/cli without `loadSpec`.

- **One file:** @clo4/cli, Commander, Yargs, citty, sade, Cliffy, Stricli, gunshi and the `parseArgs` CLI. sade has no command groups, so it has no group help.
- **A file per group:** @clo4/cli, citty, Cliffy, Stricli and gunshi, whose docs show how to load code from another file when a command line needs it, and the `parseArgs` CLI, which uses `import()`. Stricli and gunshi keep every command's definition in the entry and load only its action.

citty and Cliffy load every group's file to print root help, and citty does the same for an unknown command. Their group files import the library, so the bundler moves the library into a shared chunk that every run also loads.

oclif has no large CLI, because it loads each command from its own file through a manifest, which a single bundle can't reproduce. Cac, Clipanion, Effect, Optique, clerc, cmd-ts and brocli have no large CLI yet.

Help times are for output piped to another program. At a terminal, Node takes longer to set up `process.stdout`, which @clo4/cli doesn't use for help.

## API and compatibility

The package uses ECMAScript modules (ESM), includes TypeScript declarations and has no runtime dependencies. Its named runtime exports are `run`, `spec`, `command`, `printError`, `help`, `helpCommand` and `completion`. The default export is an object containing those same seven values.

Public types include `Spec`, `Subcommand`, `Option`, `Arg` and `ActionInit`. The [type definitions](https://github.com/clo4/cli/blob/main/src/types.ts) document each field; the [entry point](https://github.com/clo4/cli/blob/main/src/index.ts) lists all exports.

The runtime API follows semantic versioning. The testing module may introduce stricter validation rules in minor or patch releases to catch incorrect or undefined behavior.
