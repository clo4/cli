---
title: Suggest values from application data
description: Work out an argument's completions when the user presses Tab, and test them.
---

Put a suggester on the argument whose values come from application data. When the shell asks for completions, the library reads the line, finds the argument the word is for, and calls its suggester.

This example reads deployment targets from a JSON file beside the CLI module. Create `targets.json` with an array of names:

```json
["staging", "production"]
```

## Write the suggester

Export the suggester as an ordinary function so it can be tested without a shell:

```ts
// targets.ts
import { readFile } from "node:fs/promises";
import type { SuggestInit } from "@clo4/cli";

export async function targets({ word }: SuggestInit) {
  const names: string[] = JSON.parse(await readFile(new URL("./targets.json", import.meta.url), "utf8"));
  return names.filter((name) => name.startsWith(word));
}
```

A suggester gets what the action would get from the line typed so far: `path`, `args`, `argSeparatorIndex` and `options`, as strings, since no argument's parser runs while completing. `word` is the value being typed. For `--target=prod`, it's `"prod"`.

Return strings, or objects with `name` and `description` when the shell can show more. A suggester can be synchronous or asynchronous.

## Attach it to the argument

```ts
// demo.ts
import * as CLI from "@clo4/cli";
import { targets } from "./targets.ts";

const spec = CLI.spec({
  name: "demo",
  options: [
    {
      name: "--target",
      description: "Deployment target",
      args: { name: "target", suggest: targets },
    },
  ],
  subcommands: [CLI.completion],
  action({ options }) {
    console.log(options.get("--target"));
  },
});

CLI.run(spec);
```

`suggest` works the same way on positional arguments. [Install the completion script](./install-completion.mdx), then complete a value after `demo --target`.

An argument can have several suggesters, as in `suggest: [targets, recentTargets]`. They run at the same time, and their values are offered in the order they're listed, after the argument's `suggestions`. A value is offered once.

Suggestions do not constrain parsing. If execution must reject an unknown target, check the supplied name in the action, or give the argument a [parser](../concepts/parsers.mdx).

## Read the rest of the line

A suggester can depend on what was typed before the value. This one suggests the branches of the remote given with `--remote`:

```ts
args: {
  name: "branch",
  suggest: ({ word, options }) => branchesOf(options.get("--remote") ?? "origin").filter((name) => name.startsWith(word)),
},
```

`options` reads the options the way an action does, so an option that wasn't typed gives its default.

## Test the suggester

With the example's `targets.json` beside `targets.ts`, test the function on its own:

```ts
import type { SuggestInit } from "@clo4/cli";
import { expect, test } from "vitest";
import { targets } from "./targets.ts";

test("target completion filters by the word", async () => {
  expect(await targets({ word: "prod" } as SuggestInit)).toEqual(["production"]);
});
```

To test what the shell would be offered, with the parser choosing the argument, call [`CLI.complete`](../concepts/help-and-completion.mdx#complete-a-command-line-anywhere):

```ts
expect(await CLI.complete(spec, ["--target"], "prod")).toEqual([{ name: "production" }]);
```

A separate shell check confirms installation and insertion behavior.

## Keep completion responsive

Each request starts a fresh process. Move execution-only initialization into actions, and avoid expensive imports at module scope.

If a suggester queries a remote service, choose how your application handles an unavailable service. Returning an empty list lets completion carry on without suggestions from that source. Keep error reporting out of stdout, because the completion script reads it as suggestions.
