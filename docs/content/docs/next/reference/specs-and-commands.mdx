---
title: Specs and commands
description: The objects that describe a command line, and the functions that type them.
---

A CLI is one [`Spec`](#spec): a root command, with options, arguments and subcommands below it. Every field is plain data, so a spec can be written as a literal, built by code, or read from a file and given actions afterwards. [Options](../concepts/options.mdx), [Arguments](../concepts/arguments.mdx) and [Commands](../concepts/subcommands.mdx) explain the fields with examples. [Parsing behavior](./parsing-behavior.mdx) covers the rules that involve several of them.

```ts
import * as CLI from "@clo4/cli";
```

Every function is a named export, and the default export has the same functions, so `import CLI from "@clo4/cli"` works too.

## `spec(definition)` [#spec-function]

Returns `definition` unchanged, typed as a [`Spec`](#spec). It's there for TypeScript: each command's `action` gets `args` and `options` typed from that command, at any depth. Positional arguments arrive as a tuple, and `options.get` accepts only the names of the command's own options and of the persistent options above it.

```ts
const spec = CLI.spec({
  name: "demo",
  options: [CLI.help],
  args: { name: "file" },
  action({ args: [file], options }) {
    // file: string
  },
});
```

It adds nothing at runtime. A spec that isn't written as one literal, like one read from JSON, can skip it and be typed as `Spec` directly.

## `command(definition)` [#command-function]

Returns `definition` unchanged, typed as a [`Subcommand`](#subcommand). Use it for a command defined apart from the spec that uses it: in its own module, or as what a [`loadSpec`](#subcommand-loadspec) returns. Its actions are typed like those in [`spec`](#spec-function), except that they can't see the persistent options of the commands it's placed under.

## `Spec` [#spec]

The root command. It has every field of a [`Subcommand`](#subcommand) except `loadSpec`, and its `name` is a single string: the program's name, as help and the completion scripts show it.

## `Subcommand` [#subcommand]

A command. Commands nest through `subcommands`, and the parser selects the deepest one the command line names. A parent's action doesn't run when a child is selected.

### `name` [#subcommand-name]

`string | [string, string, ...string[]]`

The command's name, or its aliases. Names are case-sensitive. Use a string for one name and an array for two or more.

### `description` [#subcommand-description]

`string`

Shown in help. Its first line is also what the completion scripts show beside the name.

### `args` [#subcommand-args]

`Arg | [Arg, Arg, ...Arg[]]`

The command's positional [arguments](#arg), in order. Use an object for one and an array for two or more. Required arguments come before optional ones, and only the last can be variadic.

### `options` [#subcommand-options]

`[Option, ...Option[]]`

The [options](#option) the command accepts, including the persistent options it passes down.

### `subcommands` [#subcommand-subcommands]

`[Subcommand, ...Subcommand[]]`

The commands below this one.

### `parserDirectives` [#subcommand-parserdirectives]

How the parser reads tokens at this command. Each field is inherited on its own, so a subcommand changes one by setting it, and turns a boolean off with `false`. [Parser settings](../concepts/parser-settings.mdx) explains each with examples.

| Field                          | Type                       | Default | Effect                                                                                                                                                             |
| ------------------------------ | -------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `flagsArePosixNoncompliant`    | `boolean`                  | `false` | Read option names literally instead of chaining short names, so `-abc` is one option. A token that looks like an option but names none is a positional argument.   |
| `optionsMustPrecedeArguments`  | `boolean`                  | `false` | Stop reading options after the first positional argument. Later tokens, including `--`, are arguments.                                                             |
| `optionArgSeparators`          | `string \| [] \| string[]` | `"="`   | What joins an option's name to its value in one token. A subcommand's list replaces the inherited one. An empty array turns them off, though `-p3000` still works. |
| `subcommandsMatchUniquePrefix` | `boolean`                  | `false` | Accept an unambiguous start of a visible local subcommand's name, like `bu` for `build`. Hidden and inherited subcommands still need their exact names.            |

### `hidden` [#subcommand-hidden]

`true`

Leave the command out of help and completion. Its names still work.

### `isPersistent` [#subcommand-ispersistent]

`true`

Let the descendants of this command's parent use it too, like `{ ...CLI.helpCommand, isPersistent: true }` for `demo remote help`. There it matches only its exact name, a descendant's own subcommand with the same name wins, and help doesn't list it. Where a descendant takes positional arguments, its first argument can only be this command's name after `--`.

### `requiresSubcommand` [#subcommand-requiressubcommand]

`true`

The command takes no positional arguments. Leaving out a subcommand still runs the command's action, or prints its help if it has none.

### `action` [#subcommand-action]

[`Action`](./running.mdx#action)

What runs when the command is selected. A command without one prints its help.

### `loadSpec` [#subcommand-loadspec]

`() => Subcommand | Promise<Subcommand>`

Give the command in full only when a command line enters it, so a large CLI builds just the commands it uses. Return the command to stay synchronous, or a promise of it to `import()` it from another module. Parsing waits only when a command on the line returns a promise.

The parser, help and completion carry on with the loaded command in place of this one, and neither object is changed. Beside a `loadSpec`, a command sets only what its parent reads before then: `name`, `description`, `hidden` and `isPersistent`. [Load commands on demand](../guides/loading-commands.mdx) walks through it, and the [spec checks](./testing.mdx) report a loaded command that disagrees with its stub.

## `Option` [#option]

A named input. An option without `args` is a flag: read it with `has`, or with `count` if it repeats. An option with `args` takes values: read them with `get` or `all`. See [Options](../concepts/options.mdx).

### `name` [#option-name]

`string | [string, string, ...string[]]`

The option's name, or its aliases, written with their prefix: `-v`, `--verbose`, or `/v` on a CLI that wants it.

### `description` [#option-description]

`string`

Shown in help, followed by the defaults and what the argument's parser accepts.

### `args` [#option-args]

`Arg | [Arg, Arg, ...Arg[]]`

The [arguments](#arg) the option takes. Each use replaces the values of the use before it, unless the option is repeatable.

### `isPersistent` [#option-ispersistent]

`true`

Let the commands below this one use the option too. Help lists it under "Global flags" there. [`CLI.help`](./built-ins.mdx#help) is persistent.

### `isRepeatable` [#option-isrepeatable]

`true | number`

Allow more than one use. `true` allows any number, and a number is the most allowed. An option with arguments collects the values of every use, in order. A flag adds one per use, so `count` says how many times it was given.

### `isRequired` [#option-isrequired]

`true`

The command line has to use the option. A default doesn't count, and an option action, like `--help`, skips the check.

### `dependsOn` [#option-dependson]

`[string, ...string[]]`

Names of options that have to be used with this one. Names resolve where this option is used. Defaults don't count, and an option action skips the check.

### `exclusiveOn` [#option-exclusiveon]

`[string, ...string[]]`

Names of options that can't be used with this one, in either order. Names resolve where this option is used. Defaults don't count, and an option action skips the check.

### `requiresSeparator` [#option-requiresseparator]

`true | string`

The value has to be attached with a separator, like `--color=auto`. `true` accepts any enabled separator, and a string requires that one. It has to be one of the command's [`optionArgSeparators`](#subcommand-parserdirectives).

### `ref` [#option-ref]

`string`

A second key to read the option by, for an option that shares a name with a different option on a command above or below it. Reading by the name gives whichever was used last, and reading by the ref always gives this one. The spec checks require a ref on both options and allow it nowhere else.

### `hidden` [#option-hidden]

`true`

Leave the option out of help and completion. Its names still work.

### `action` [#option-action]

[`Action`](./running.mdx#action)

Runs in place of the command's action when the option is used, like `--help` or `--version`. The last option with an action wins. It skips argument counts, required options and option rules, and no argument's parser runs, so it reads every value as typed. An unknown option or a malformed value still fails.

## `Arg` [#arg]

A positional argument, or an argument of an option. Its value is the string that was typed, unless its parser turns it into something else. See [Arguments](../concepts/arguments.mdx).

### `name` [#arg-name]

`string`

Shown in help, like `<file>`.

### `description` [#arg-description]

`string`

Shown in help for a command's positional arguments, with the default. An option's argument description isn't shown.

### `isOptional` [#arg-isoptional]

`true`

The argument can be left out. Arguments are required unless they say otherwise.

### `isVariadic` [#arg-isvariadic]

`true`

Take one or more values, or zero or more with `isOptional`. Only the last argument can be variadic, and its values stay in the same array as the others.

### `default` [#arg-default]

`string`

The value used when the argument is left out. It goes through the argument's parser like a typed value.

- A positional argument's default is added to `args`, so the argument has to be optional.
- An optional option argument's default is added when the option is used without it, so a bare `--inspect` can mean `--inspect=9229`.
- A required option argument's default is what `get` and `all` return when the option isn't used. `has` and `count` still say it wasn't.

Defaults fill the arguments left out in order, up to the first one without a default. They never count as a use of an option, for `isRequired`, `dependsOn` or `exclusiveOn`.

### `parse` [#arg-parse]

[`StandardSchemaV1`](./standard-schema.mdx#standardschemav1)

Turn the value into what the action receives, or reject it. Use a [built-in parser](./parsers.mdx), or a [Standard Schema](./standard-schema.mdx) from Zod, Valibot, ArkType or another library. Every argument's parser runs before the action, and every rejected value is reported together. Each value of a variadic argument or a repeatable option is parsed on its own.

### `suggestions` [#arg-suggestions]

`(string | Suggestion)[]`

Values completion offers, written out. They don't limit what the parser accepts.

### `suggest` [#arg-suggest]

[`Suggester | [Suggester, Suggester, ...Suggester[]]`](./completion.mdx#suggester)

Work out the values completion offers when the user presses Tab. Suggesters run at the same time, and their values follow `suggestions`, in order. They don't limit what the parser accepts.

### `template` [#arg-template]

[`Template`](./completion.mdx#template)

Complete file or folder paths, through the shell's own path completion.

An argument without `suggestions`, `suggest` or `template` offers what its parser accepts.

## Helper types [#helper-types]

| Type                      | Meaning                                            |
| ------------------------- | -------------------------------------------------- |
| `NonEmptyArray<T>`        | An array with at least one element.                |
| `SingleOrArray<T>`        | One value, or an array of two or more.             |
| `SingleOrArrayOrEmpty<T>` | One value, or an array of none, or of two or more. |
