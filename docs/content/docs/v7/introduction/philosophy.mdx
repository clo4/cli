`@clo4/cli` is described as _a magical CLI framework, with no magic_. Four ideas sit behind that line, and each answers a different question a user asks:

- **Simplicity**: how much do I have to know?
- **Excellence**: how well is it done?
- **Magic**: how does it feel to use?
- **No magic**: will it surprise me?

Together they make one promise. What you learn is small, it keeps applying, and it pays off more than you expected.

## Simplicity

A CLI is a plain object. Commands, options and arguments are objects with fields, and a command lists its options and subcommands in arrays. There is no builder to call in the right order, no class to extend, and no string syntax to learn for defining an option or its arguments.

There are only a few concepts, and they compose. An option takes [arguments](../concepts/arguments.mdx) the same way a command does. An argument's [parser](../concepts/parsers.mdx) is built from smaller parsers, so building a parser for `30s` needs no new ideas once you know the basic parsers. Hidden, persistent, variadic, defaults, and more are all just fields on objects.

## No magic

Once you understand the concepts, there are no surprises. If you expect something to work, it does. Nothing behaves one way in one place and another way elsewhere.

### `CLI.spec` is an identity function

`CLI.spec` returns the object you pass it. Its only job is to give TypeScript a place to infer your action's inputs from.

```ts
const definition = { name: "greet", args: { name: "who" } };

CLI.spec(definition) === definition; // true
```

This is fundamental to the library. The spec is not a special, processed object. It's not a class either. It's a grammar definition that the parser uses to know what commands, options, and arguments exist.

### Built-ins aren't special

`CLI.help` is an option. `CLI.helpCommand` and `CLI.completion` are subcommands. You put them in your spec like any option or subcommand you write, because that's what they are. Here is the whole of `CLI.help`, written as you could write it:

```ts
const help: CLI.Option = {
  name: ["-h", "--help"],
  description: "Print a help message",
  isPersistent: true,
  action({ help }) {
    CLI.print(help().trimEnd());
  },
};
```

An option's action runs in place of the command's action, which is all a help or version flag needs:

```ts
const version: CLI.Option = {
  name: ["-V", "--version"],
  description: "Print the version",
  action() {
    CLI.print("1.4.0");
  },
};
```

Since the built-ins are objects, you can copy and change them like any other. This hides the help command from help and completion, and keeps it working:

```ts
const helpCommand = { ...CLI.helpCommand, hidden: true };
```

The built-ins rely on the library's internals through public helpers, the way your code would. The completion command's own `--shell` option uses an argument's parser the same way any spec does.

### A spec is just data

Nothing about a spec has to be written in TypeScript. It can come from a JSON or YAML file, be assembled at runtime, or be generated by another tool. Attach the functions afterwards and pass it to `run`:

```ts
import { readFileSync } from "node:fs";
import * as CLI from "@clo4/cli";

const spec: CLI.Spec = JSON.parse(readFileSync("deploy.json", "utf8"));
spec.options = [CLI.help];
spec.action = ({ args, options }) => {
  console.log(args, options.has("--dry-run"));
};

CLI.run(spec);
```

You give up inferred types this way, since TypeScript can't see the file. The parser, help and completion behave exactly as they would for the same object written inline.

## Magic

From that one spec object, you get:

- **Types.** The action's arguments and options are typed from the definition. An option with a default is a `string`, an argument with `CLI.number` is a `number`, and an unknown option name is a type error.
- **Help.** Usage lines, descriptions, defaults and each parser's pattern, for every command.
- **Completion.** Subcommands, options and values for Bash, Zsh, Fish, PowerShell and Nushell, from the same reading of the line that the parser does.
- **Errors.** Every problem with the invocation:

```console
$ serve --wait 30x
Error: Option --port is required, but wasn't found
Error: Invalid value "30x" for --wait: expected ms | s | m after "30"

Usage:
  serve --port <port> [flags]

Flags:
  --port <port>      (int from 1 to 65535)
  --wait <duration>  (<int>(ms|s|m))
```

## Excellence

The implementation is held to a high standard.

- There are no runtime dependencies.
- There are extensive benchmarks that try to run the alternatives in a realistic and advantaged way
- The design of the library must be ideologically simple and composable.
