title: Help and completion
description: How help and completion use command definitions and argument metadata.
---

Help and completion use the arguments, options and subcommands in your spec. Add all three built-ins to every CLI, unless you have a reason to leave one out. Users expect `--help` on every command, and completion is how most of them find a command's subcommands and options.

Put `CLI.help` in the root's options, and `CLI.helpCommand` and `CLI.completion` in its subcommands:

```ts
import * as CLI from "@clo4/cli";

const spec = CLI.spec({
  name: "demo",
  options: [CLI.help],
  subcommands: [
    {
      name: "build",
      description: "Build a project",
      args: {
        name: "directory",
        isOptional: true,
        template: "folders",
      },
      action({ args }) {
        console.log(args);
      },
    },
    CLI.helpCommand,
    CLI.completion,
  ],
});

CLI.run(spec);
```

The commands below use `demo` for your installed executable. For this example, substitute `node demo.ts` when requesting help. Completion scripts need the installed command name.

## Help

`CLI.help` is a persistent option named `-h` and `--help`. It prints help for the selected command, so `demo build --help` describes `build`.

`CLI.helpCommand` is a subcommand. `demo help build` prints the same help. For nested commands, use the whole path, as in `demo help remote add`. Completion also suggests command names along that path.

The built-ins are plain objects. Copy one with object spread to change its fields:

```ts
{ ...CLI.help, description: "Show help" }
```

To allow help after a descendant command, add `{ ...CLI.helpCommand, isPersistent: true }`. Then `demo build help` prints help for `build`. [Persistent subcommands](./subcommands.mdx#persistent-subcommands) explains name matching and positional arguments in that configuration.

## Completion suggestions

An argument can offer fixed suggestions, dynamic suggestions or file paths. These fields work on both positional and option arguments.

Completion follows the command-line parser's command scope and option rules. It omits hidden names, conflicting options and options at their repeat limit. Suggestions do not validate input. An argument's [parser](./arguments.mdx#parsing-values) enforces restrictions on accepted values, and completion offers the values that parser lists when the argument has no suggestions of its own.

### Static suggestions

Set `suggestions` to a list of strings or objects with `name` and `description`:

```ts
args: {
  name: "environment",
  suggestions: [
    { name: "staging", description: "Test environment" },
    { name: "production", description: "Live environment" },
  ],
},
```

For short lists without descriptions, use `suggestions: ["staging", "production"]`.

### Dynamic suggestions

A suggester is a function that works out suggestions when the user presses Tab. Set `suggest` on the argument it completes:

```ts
import * as CLI from "@clo4/cli";

const spec = CLI.spec({
  name: "demo",
  options: [
    {
      name: "--target",
      description: "Deployment target",
      args: {
        name: "target",
        suggest: async ({ word }) => ["staging", "production"].filter((name) => name.startsWith(word)),
      },
    },
  ],
  subcommands: [CLI.completion],
  action({ options }) {
    console.log(options.get("--target"));
  },
});

CLI.run(spec);
```

A suggester returns the same shapes as `suggestions`. It gets what the action would get from the line typed so far, and `word`, the value being typed. The library selects the argument and formats the results for the shell.

[Suggest values from application data](../guides/suggest-values.mdx) shows a suggester that reads application data, one that reads the rest of the line, and how to test them.

### Files and directories

Set `template: "filepaths"` to suggest files and directories. Use `template: "folders"` for directories only:

```ts
args: { name: "config", template: "filepaths" },
```

Templates affect completion only. They do not check whether a supplied path exists or has the expected type.

## Completion startup

Each completion request starts a CLI process. It runs the relevant suggesters without running the selected command's action.

Put application initialization inside actions when only command execution needs it. Work at module scope runs during completion too, including imported modules' initialization.

The scripts set `SHELL_COMPLETION_GENERATOR` to the shell name while requesting suggestions. If initialization must happen before `CLI.run`, use that variable to skip it during completion:

```ts
if (!process.env.SHELL_COMPLETION_GENERATOR) {
  await loadPlugins();
}
```

Here, `loadPlugins` is application code. Keep any initialization that your suggesters need available during completion.

## Installing the scripts

[Install shell completion](../guides/install-completion.mdx) shows startup configuration for Bash, Zsh, Fish, PowerShell and Nushell. Generate the script at shell startup so it matches the installed CLI. The command must be available by its installed executable name.

## Complete a command line anywhere

The shell scripts are one use of `CLI.complete`. It says what the word being typed can become after the words before it, the way the parser reads the line, so a prompt, a REPL or a script for another shell completes exactly as the built-in shells do:

```ts
const completions = await CLI.complete(spec, ["deploy", "--target"], "pro");
// [{ value: "production" }]
```

Each completion has a `value`, and a `description` and `open` when they apply. An open value needs more text after it, like `1920x`, so a shell adds no space. Pass `{ optionsNeedDash: true }` to offer options only once the word starts one of their names, which is what the Bash, Fish, PowerShell and Nushell scripts do.
